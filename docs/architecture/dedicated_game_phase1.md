# Game別EC2: 検証用の境界と状態モデル (Phase 1)

この段階はリポジトリ上の契約とテストだけ。新規モデルは従来のLambda配布物に含めない。既存環境の SYS-002（単一実行）、
既存の設定・CDK入口・API・Discord・実行経路は変更しない。新しいAWSリソースや
権限、DNS、認証情報は作成・検証しない。

## 環境の境界

`infrastructure.dedicated.deployment.validate_sandbox` は要求値と、信頼できる設定から渡される
期待値の環境・アカウント・リージョン・名前空間がすべて一致する場合のみ通す。
どれも省略できず、別アカウントの `dedicated-sandbox` /
`wc2-sandbox` 系以外は対象外。従来の `dev` は実利用環境であり、既定値にしない。
この関数は本番を配布できる入口ではない。

拒否する境界は、リポジトリにある実利用アカウントと既存Data EBS・VPC・
サブネット・ホストゾーン、Parameter Storeの旧名前空間とDNS名。
秘密値は読まず、候補パスは検証環境の名前空間配下、候補DNS名は検証子ゾーン
配下に限る。ハードコードした実利用のIDや接続先を複製しない。実AWSの
Caller Identity・所有権・権限・tagの照合は後続であり、この検査では代替できない。

## Game単位の実行契約

- 別Gameの起動受付は独立し、A/B/Cを同時に受理できる。台数の固定上限や
  ワールド間の操作ロックは置かない。AWS側の容量不足等は後続の実行境界で扱う。
- 同一Gameの別操作は進行中に受理しない。同じ割当て・要求ID・操作の再送では
  同じ受付記録を返す。要求IDは受付側で実行者と要求に結び付けて渡す。
- 操作結果はGame・world世代・host世代・backendの割当て版・操作版で照合する。
  heartbeatは成功した現在の起動に紐づけ、連番が後退する更新は不採用とする。
  不明な結果はUNKNOWNとして受付を保持し、停止・削除へ推測で遷移しない。
- hostの廃棄を受理するには、保存済みの停止確認、対象Gameと世代に対応する
  完了済みSnapshotと復元用manifest、保持指定なしが必要。manifestは最新の保存版
  （正常STOPの操作版）に結びつける。同じhostでも以前の保存点では廃棄できない。
  結果確認後に
  host世代を更新する。保持指定・現状態・証跡は実操作直前にも再検証する
  必要があり、このモデルをAWSの検証済み証跡として使わない。
- backend切替は保存済みの停止または確認済みの不在、操作なし、旧割当て版の
  一致を要求する。実際の移行では旧writerを先に停止してから、保存先で
  割当ての条件付き更新（CAS）を行う。割当て版が古い処理は新writerと併存させない。

モデルは単一Gameの純粋な遷移。テスト内の受付記録は永続テーブルの設計ではない。
競合する同時要求の条件付き書込み、実保存確認、操作結果の再照合、RESET、
復元、DNS、自動退避スケジュール、利用者向け画面・権限は後続の作業とする。

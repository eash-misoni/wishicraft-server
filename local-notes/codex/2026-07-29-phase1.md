# Wishicraft Phase 1 作業記録（2026-07-29〜再開直前）

> 学習用の時系列記録。対象はセッション開始から、RCON を host firewall で実効的に localhost 限定にする実装の完了報告までである。
>
> RCON password、AWS credential、SSO 情報、ローカル AWS profile の値は記載しない。Parameter 名、artifact checksum、公開プロフィール UUID など、秘密ではない設計情報だけを必要最小限に扱う。

## 1. この期間の全体像

Phase 0 で設定読込・CDK synth・CI の土台を作ったあと、Phase 1 の Minecraft サーバーを「ネットワーク → IAM → EC2 → 永続ディスク → mount guard → Java → Minecraft artifact/runtime → RCON」という小さな実装単位へ分割した。

一貫した原則は次のとおりである。

- `null` や未確定値は推測で補完しない。
- deploy、AWS API、SSM の実値取得、DNS 変更、実 EC2 起動は local test/synth と分け、明示承認があるまで実行しない。
- RCON password は Git、CDK context、CloudFormation template、user data、fixture、ログへ置かない。
- world data は root EBS ではなく retain された data EBS に置く。
- 失敗時に危険な代替経路（root volume 上で Minecraft を起動する、既存 volume を format する、広い IAM を付ける）へ進まない。

この分離により、prod の placeholder を勝手に埋めずに読み込みつつ、必要な操作では不足項目を明示して止められる。

#### IAM の要点

EC2 role の trust principal は `ec2.amazonaws.com` のみとした。SSM Agent に必要な action は AWS 公式 managed policy を参考に repository 管理の explicit policy へ写し、Parameter Store 読取を core statement から分離した。

RCON 用 statement は stage の Parameter 名から正確な ARN を構成し、`ssm:GetParameter` だけを許可する。先頭 `/` をそのまま ARN の `parameter/` に連結して二重 slash にならないよう正規化した。`GetParameters`、`GetParametersByPath`、history、describe、write、不要な `kms:Decrypt` は追加しなかった。

#### EC2 と EBS の要点

- instance は public subnet に置き、稼働中のみ dynamic public IPv4 を得る。Elastic IP は作らない。
- root EBS は再作成可能な OS 領域で、data EBS はゲームの永続領域である。
- attachment API 上の `/dev/sdf` は Nitro OS 上の device 名を保証しない。そのため将来の mount は `/dev/sdf` に依存しない。

### 2026-08-上旬: data EBS の安全な XFS 初期化と mount guard

#### 利用者の確定設計

filesystem 未定義だったため、新規 Decision `D-053` として次を採用した。

- data EBS は partition を作らず volume 全体を **XFS** にする。
- filesystem/partition/signature が一切ない空 volume だけ `mkfs.xfs` を一回行う。
- 既存 XFS は再 format せず再利用する。
- 非 XFS、partition table、未知 signature は `wipefs` や強制 format をせず fail-closed。
- `/etc/fstab` は device 名でなく UUID を使い、`defaults,nofail` とする。
- OS/SSM の復旧経路は `nofail` で確保するが、Minecraft は mount guard が成功しない限り起動しない。

#### 実装

- `storage.data.filesystem_type: xfs` を dev/prod の公開設定、schema、required validation、accessor、tests に追加。
- `infrastructure/bootstrap/data_volume_mount.sh` を repository 管理の独立 script とした。
- EBS volume ID と Nitro NVMe serial を正規化後に**完全一致**させ、期待 volume の実 device だけを選択する。
- 有限 retry で attachment を待つ。timeout 時は format/fstab/mount を一切しない。
- Wishicraft 管理行を持つ UUID fstab entry を冪等に管理し、競合 entry は置換せず失敗する。
- `wishicraft-data-volume.service` は oneshot service とし、user data から `enable --now` する。guard は marker だけを信じず、mount source/UUID/type を実測して検証する。

command stub と一時 directory を用い、実 block device の format/mount/root 操作はしなかった。空 volume、既存 XFS、非 XFS、partition table、timeout、別 volume の mount、fstab 競合、冪等再実行を検証した。

`nofail` と fail-closed は矛盾しない。前者は OS boot の可用性、後者はゲームデータを誤った filesystem へ書かない安全性を扱う。

### 2026-08-中旬: RCON SecureString と Route 53 の依頼、user data 16 KiB 問題

#### 利用者の依頼

次の対象は、stage 固有 RCON SecureString を EC2 起動時に読み込んで RCON を外部非公開で有効化すること、および dev A record の UPSERT/DELETE CLI だった。AWS 接続、secret 値表示、DNS 変更、commit/push は禁止された。

初期実装では data mount、Java、artifact、game setup、RCON configure の script 本文を CloudFormation user data に heredoc として直接埋め込んでいた。その方式では EC2 user data の Base64 化前上限 **16,384 bytes** を超えるおそれが判明した。

利用者は、S3/追加 IAM/CloudFormation Init を推測で導入する代わりに、決定的 tar.gz bundle と小さな runner へ置換することを承認した。

#### bundle 方式の実装判断

追加した中心ファイル:

- `infrastructure/constructs/bootstrap_bundle.py`: allowlist から deterministic tar.gz を生成。
- `infrastructure/bootstrap/bootstrap_runner.sh`: user data 内で checksum 検証、archive 検査、展開、順序実行を行う。
- `infrastructure/constructs/data_volume_bootstrap.py`: 旧 heredoc を除去し、bundle Base64、SHA-256、固定引数を runner へ渡す。
- `tests/unit/test_bootstrap_runner.py`: bundle と archive の安全性を検証。

bundle の metadata は file order、mtime、uid/gid、owner/group、mode、gzip header を固定する。同じ source を二回独立に bundle 化し、byte 単位で一致することを test する。secret 値は bundle に入れず、RCON Parameter 名だけを runner environment に渡す。

user data が展開後に実行する順序は、既存の fail-closed 契約を保つ。

1. data volume mount
2. mount verify
3. Java runtime install/verify
4. Minecraft user と Game directory prepare
5. verified artifact install
6. game setup
7. RCON configure

途中の script が非 zero なら `set -euo pipefail` により後続、Minecraft 起動へ進まない。

#### 途中で起きたエラーと修正

1. 大きな heredoc を含むファイル全置換 patch は編集ツールの構文制約や context mismatch で失敗した。
   - これは runtime の技術的 blocker ではない。
   - import、allowlist、runner 呼出、旧 heredoc の 1 block 削除、path 修正を局所 patch に分解して直した。
2. 最初の user data 測定は `AWS::EC2::Instance` を決め打ちして `StopIteration` になった。
   - synth template の user data は resource type 決め打ちで探してはいけない。
   - template を再帰走査し、`UserData` key を列挙して候補数・logical ID・resource type・property path を診断する helper に直した。
3. `Fn::Base64` operand を通常の Base64 文字列とみなして decode し、次のエラーになった。

```text
AttributeError: 'dict' object has no attribute 'encode'
```

   - 実体は `Fn::Base64` の中の `Fn::Join` だった。
   - `Fn::Join` を構造どおり復元し、既知の data volume `Ref` のみ deterministic な representative value に解決して、Base64 化**前**の UTF-8 bytes を測るよう修正した。未知 intrinsic は推測で解決しない。

#### 実際の synth output からの測定

代表的な synth command:

```sh
npx --no-install cdk synth --context stage=dev --context phase=1 --output /private/tmp/wishicraft-synth-<temporary-id>
```

測定は `manifest.json` の stack artifact/template file を読む。template を再帰的に走査して、最終的に `MinecraftInstanceC550B42B` の `Properties.UserData` を一件だけ対象と確認した。operand は `Fn::Base64` → `Fn::Join` だった。

bundle 接続完了直後の値は **8,662 bytes**（残り **7,722 bytes**）だった。これは bundle 単体の圧縮サイズではなく、runner、Base64 bundle、checksum、引数、Parameter 名を含む CloudFormation が EC2 へ渡す平文 user data の実測値である。

### 2026-08-中旬: archive の事前安全検査

利用者は「SHA-256 が正しい archive でも安全な member しか展開しない」ことを要求した。runner は checksum 成功後、**展開前**に archive 全体を検査するようにした。

許可対象は bundle helper と runner の単一 allowlist から導く bootstrap source であり、当初の 5 本は次の member 名だった。

```text
data_volume_mount.sh
java_runtime_install.sh
minecraft_artifact_install.sh
minecraft_game_setup.sh
minecraft_rcon_configure.sh
```

後の firewall unit 追加時は `minecraft_rcon_firewall.sh` も同じ allowlist に加えた。

runner の安全条件:

- `set -euo pipefail` と `umask 077`。
- root 専用 temporary directory と `trap` cleanup。
- SHA-256 mismatch、truncated/corrupt archive は拒否。
- allowlist と完全一致しない member、必須 member の欠落、重複 path、directory を拒否。
- absolute path、`..` traversal、symlink、hardlink、FIFO/device など regular file 以外を拒否。
- 同じ archive implementation を用いて検査・展開し、検査完了前には書き込まない。
- 展開後も expected file が regular file / non-symlink / expected mode であることを確認する。

test は正常 bundle に加え、`/absolute/path`、`../escape.sh`、`dir/../../escape.sh`、symlink、hardlink、unexpected regular file、missing member、duplicate member、FIFO を生成する test-only helper を使用した。各失敗で、展開先外への書込、script marker、後続 script 実行がないこと、temporary directory cleanup を確認した。本番 `build_bundle()` を不正 archive を受け入れるよう緩めてはいない。

archive safety 追加後も synth template から再測定し、RCON 作業前の測定は **12,228 bytes** だった。数値を固定 snapshot として source に埋めず、test ごとに synth output から算出する。

### 2026-08-中旬: RCON SecureString の安全な runtime 配布

#### 設定から `server.properties` までの経路

```text
config/secrets.example.yaml の stage 別 Parameter 名
  -> config loader / accessor
  -> MinecraftStack / DataVolumeBootstrap
  -> user data の environment（Parameter 名だけ）
  -> minecraft_rcon_configure.sh
  -> aws ssm get-parameter --with-decryption
  -> atomic な server.properties 更新
```

RCON password の実値はこの経路の runtime script 内部だけで扱い、CDK/template/user data/Git/test snapshot には含めない。

#### 実装した安全条件

- IAM は対象 stage の exact Parameter ARN への `ssm:GetParameter` に限定する。
- `aws ssm get-parameter --with-decryption --output json` の結果を `python3` で読み、`Type == SecureString` を確認する。
- Parameter 不在、CLI 失敗、復号不能、空値、短すぎる値、NUL/CR/LF は fail-closed。
- password を command line、stdout/stderr、error text、marker、不要な temporary file に出さない。
- shell metacharacter を shell として評価しない。
- `server.properties` の RCON 関連 key は重複なしで deterministic に生成する。非 secret 設定の危険な drift は黙って上書きしない。
- temporary file を同 directory に置き、`chown root:minecraft`、`chmod 0640`、確認後に atomic replace する。失敗時に既存の正常設定を壊さない。

最初の fake command test ではローカル環境に `timeout` command がなく、次の失敗が出た。

```text
timeout: command not found
```

実 EC2 の挙動を変えるのでなく、test-only fake `timeout` executable を追加して command stub の閉包性を直した。

RCON test は正常取得/再実行、AWS CLI failure、Parameter 不在、type 不一致、空/CR/LF、shell metacharacter、mount guard failure、owner/mode failure、stdout/stderr 非漏洩、既存設定の保存を検証した。

#### localhost 限定についての発見

Vanilla Minecraft の `server.properties` には、public Minecraft 接続を維持したまま RCON socket **だけ**を `127.0.0.1` へ bind する設定はない。`server-ip` を使えば Minecraft game socket まで影響するため、RCON 専用 loopback bind の根拠にはならない。

このため「Security Group に ingress がない」だけで socket が loopback bind されているとは記載しない。利用者に blocker を報告し、host firewall による実効的な localhost 限定を承認してもらった。

### 2026-08-中旬: nftables による実効的 localhost 限定

#### 選定と実装

Amazon Linux 2023 の package 情報を確認し、初期 AMI に `nft` があると推測せず、存在しない場合だけ既存 package install 方針に従って `dnf install -y nftables` を行う bootstrap を追加した。

- `infrastructure/bootstrap/minecraft_rcon_firewall.sh`
- `wishicraft-rcon-firewall.service`
- `minecraft_rcon_firewall.sh` を deterministic bundle allowlist に追加

RCON port は RCON configure と firewall で別々にハードコードせず、同じ generated environment 設定から渡す。秘密値は firewall に渡さない。

Wishicraft 専用 `inet wishicraft_rcon` table の input chain だけを管理する。INPUT 全体の default policy、他 table/chain、Minecraft port、SSM、outbound 通信は変更しない。要点となる rule は次のとおりである（`<rcon-port>` は設定由来）。

```nft
tcp dport <rcon-port> ip daddr != 127.0.0.1 drop
tcp dport <rcon-port> ip6 daddr != ::1 drop
```

つまり IPv4 は `127.0.0.1`、IPv6 は `::1` 宛て以外の RCON TCP を host で拒否する。socket が wildcard bind である可能性は残るが、実効的な到達性は loopback に限定する。Security Group に RCON ingress は追加しない。

rule file は root:root、0600 で保存し、`nft --check --file` が成功してから `nft --file` を実行する。reboot 用 oneshot systemd unit は `Before=minecraft.service`、Minecraft service は firewall を `Requires=` し `After=` する。firewall install/check/apply/enable のどれかが失敗すると user data は失敗し、Minecraft 起動へ進まない。

`D-011` には、Vanilla に RCON 専用 bind address がないこと、wildcard bind があり得ること、host firewall と Security Group の二層で実効的 localhost 到達性を作ることを最小限追記した。

## 3. 技術的に理解しておくべき点

### synth は deploy ではない

CDK synth は CloudFormation の構造、IAM policy、UserData、resource count を test できる。一方、AMI 上に `nft` があるか、SSM Parameter が実在するか、Minecraft が SIGTERM で world を保存するか、DNS が伝播するかは確認しない。local success を AWS 実地確認の成功と書かない。

### user data の上限は「圧縮 archive のサイズ」ではない

EC2 制限の対象は CloudFormation が `Fn::Base64` 化する前の最終 user data の UTF-8 bytes である。runner、Base64 表現、checksum、parameter name、join された token を含めた実 template operand を測る必要がある。archive が 3,968 bytes であっても、それだけでは上限充足の証拠にならない。

### checksum と member safety は別の防御層

SHA-256 は bundle 全体の改ざん/破損を検出する。しかし checksum が正しい archive に unexpected path や link が入っていないことまでは保証しない。そこで allowlist、member type、path traversal、重複、展開後 regular-file 検査を加える。

### RCON の「localhost 限定」は bind assertion と区別する

Vanilla の構成では RCON 専用 bind property がない。RCON client が `127.0.0.1` を使うこと、Security Group に ingress がないこと、nftables が loopback 以外を drop することは、**実効的到達性**の制御である。socket が `127.0.0.1` に bind されているという主張ではない。

### fail-closed の具体例

- 正しい data EBS を特定できない: mount せず Minecraft を起動しない。
- archive checksum/member 検査が失敗: 一切展開・実行しない。
- SecureString 取得/validation/atomic replace が失敗: RCON 設定を部分的に残さず起動しない。
- firewall check/apply が失敗: Minecraft service を起動しない。
